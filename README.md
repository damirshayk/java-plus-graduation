# Explore With Me

Сервис поиска мероприятий, заявок на участие, комментариев и персональных рекомендаций. Приложения `core` взаимодействуют по HTTP, рекомендательная система — по gRPC и Kafka. Удаление связанных данных также передаётся через Kafka. Внешние HTTP-запросы проходят через Gateway на порту `8080`.

## Архитектура

| Приложение | Ответственность и собственные данные |
| --- | --- |
| `discovery-server` | Реестр Eureka, порт `8761` |
| `config-server` | Настройки приложений из `infra/config-server/src/main/resources/config-repo` |
| `gateway-server` | Единая точка входа, маршрутизация по именам сервисов через LoadBalancer |
| `user-service` | Пользователи; очередь уведомлений об удалении в `cleanup_outbox` |
| `event-service` | Мероприятия, категории, подборки и их связи; маркеры очистки, `cleanup_inbox` и `cleanup_outbox` |
| `request-service` | Заявки и их статусы; маркеры очистки пользователей и мероприятий |
| `comment-service` | Комментарии; маркеры очистки пользователей и мероприятий |
| `collector` | Приём действий пользователей по gRPC и публикация в Kafka |
| `aggregator` | Инкрементальный расчёт сходства мероприятий; матрица в памяти, восстановление из Kafka |
| `analyzer` | История взаимодействий и сходства в отдельной PostgreSQL; рекомендации и рейтинги по gRPC |

Каждый сервис данных подключается к своей БД и выполняет собственные миграции Flyway. Между базами нет внешних ключей и прямых SQL-запросов: ссылка на чужую сущность хранится как идентификатор. Старый `main-service` заменён четырьмя приложениями в `core`. Прежние REST-модули статистики удалены; `/hit` и `/stats` больше не доступны.

`user-client` и `event-client` содержат общие контракты и Feign-клиенты, `api-errors` — общий формат и перевод ошибок Feign, `cleanup-events` — сообщения очистки и доставку outbox. Они не включают реализации сервисов или чужие JPA-сущности. `stats-client` содержит отдельные gRPC-клиенты Collector и Analyzer; Protobuf- и Avro-контракты находятся в `stats/serialization`. Интерфейс счётчика подтверждённых заявок принадлежит его потребителю — `event-service`.

При создании заявки и комментария пользователь и мероприятие проверяются по HTTP. Списки обогащаются пакетными запросами: имена пользователей, подтверждённые заявки и рейтинги загружаются для набора идентификаторов, а не отдельно для каждого мероприятия. Сетевые вызовы выполняются вне транзакций БД; связанные локальные изменения — в короткой транзакции.

## Конфигурация

Клиенты находят `config-server` через Eureka и загружают общие настройки из `config-repo/application.yml` и YAML своего приложения. Настройки приложения имеют приоритет над общими. Config Server работает с профилем `native` и каталогом `classpath:/config-repo/`; его конфигурация и адрес Eureka находятся в `application.properties` инфраструктурных модулей. Локальные настройки клиентов сохраняют имя приложения, адрес Eureka и параметры получения конфигурации.

- `EUREKA_SERVER_URL` задаёт адрес Eureka; по умолчанию `http://localhost:8761/eureka/`.
- `--server.port` переопределяет порт приложения. Кроме Gateway и Eureka, порты по умолчанию случайные.
- У каждого сервиса данных свои `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`. Четыре приложения `core` по умолчанию используют отдельные файловые H2 в `./data`, чтобы данные и outbox переживали перезапуск. Analyzer использует `jdbc:postgresql://localhost:55434/ewm_analyzer`, пользователь и пароль по умолчанию — `postgres`.
- Flyway создаёт схему, Hibernate проверяет её через `ddl-auto=validate`; `open-in-view` отключён.
- Таймауты Feign: подключение `1000` мс, чтение `2000` мс. Настройки резервного отображения находятся в `event-service.yml`; gRPC deadline `stats.client.timeout-ms` по умолчанию равен `1000` мс, настройки клиентов и их CircuitBreaker — в общем `application.yml`.
- Collector, Aggregator и Analyzer имеют HTTP-сервер со случайным `server.port=0` для Actuator и корректной регистрации в Eureka. gRPC-клиенты находят Collector и Analyzer по адресам `discovery:///collector` и `discovery:///analyzer`, политика распределения — `round_robin`. У gRPC-серверов `grpc.server.port=0`: в metadata Eureka публикуется отдельный фактический gRPC-порт, не HTTP-порт приложения.
- `KAFKA_BOOTSTRAP_SERVERS` задаёт адрес общего брокера; по умолчанию `localhost:9092` для проверочного окружения. Локальный `docker-compose.kafka.yml` публикует `localhost:29092`: при таком запуске переменную необходимо установить в каждом терминале приложений.
- Общие топики, веса действий, таймаут отправки и пауза повторной обработки задаются в `application.yml`; группы и параметры потребителей — в `aggregator.yml` и `analyzer.yml`. Параметры очистки и outbox остаются в YAML четырёх приложений `core`.

Не задавайте один общий адрес БД всем приложениям. Миграции новых сервисов рассчитаны на отдельные новые базы, а не на автоматическое преобразование старой БД монолита.

## Внешний API

Все внешние HTTP-запросы отправляются на `http://localhost:8080`:

| Пути | Получатель |
| --- | --- |
| `/admin/users/**` | `user-service` |
| `/users/{userId}/events/{eventId}/comments` и вложенные пути | `comment-service` |
| `/users/{userId}/requests`, вложенные пути; `/users/{userId}/events/{eventId}/requests`, вложенные пути | `request-service` |
| Остальные `/admin/**`, `/users/**`, `/events/**`, `/categories/**`, `/compilations/**` | `event-service` |

Более узкие маршруты пользователей, комментариев и заявок проверяются перед общим маршрутом событий. Gateway не публикует `/internal/**`.

Основной контракт: [API мероприятий](ewm-main-service-spec.json). Дополнительные сценарии комментариев: [Postman-коллекция](postman/feature.json).

Во всех DTO мероприятий, в том числе внутри подборок, `views` заменено на `rating` типа `double`. Рейтинг — сумма максимальных весов взаимодействий пользователей с мероприятием, а не число просмотров; дробная часть сохраняется. Публичный поиск поддерживает `sort=EVENT_DATE` и `sort=RATING` (по убыванию рейтинга); `VIEWS` оставлен как устаревший псевдоним `RATING`. Равные значения упорядочиваются по ID.

| Метод и путь | Поведение |
| --- | --- |
| `GET /events` | Каталог без записи действия `VIEW`; заголовок пользователя не требуется |
| `GET /events/{id}` | Карточка опубликованного мероприятия; `VIEW` отправляется после успешной загрузки |
| `GET /events/recommendations?size=10` | Персональные рекомендации; размер положительный, по умолчанию `10`; возвращаются только существующие опубликованные мероприятия в порядке Analyzer |
| `PUT /events/{eventId}/like` | `LIKE` после проверки участия; успешный ответ `200` без тела |

Для карточки, рекомендаций и лайка обязателен `X-EWM-USER-ID` — положительный 64-битный ID пользователя. Отсутствующий, нечисловой или неположительный заголовок даёт `400`. Отсутствующее либо неопубликованное мероприятие — `404`.

Право на лайк в этой реализации означает подтверждённую заявку и уже наступившую дату мероприятия. Это интерпретация посещения: отдельного учёта фактической явки нет. Отсутствие подтверждённого участия либо будущая дата дают `400`; недоступность проверки участия — `503`, без отправки `LIKE`.

`request-service` отправляет `REGISTER` после сохранения заявки и завершения локальной транзакции, без удержания транзакции во время gRPC-вызова. Отмена, отклонение и ошибка регистрации нового действия не создают.

## Рекомендательная система

Collector принимает Protobuf-действия `VIEW`, `REGISTER`, `LIKE` и после подтверждения Kafka завершает RPC. Действия публикуются как Avro в `stats.user-actions.v1` с ключом ID пользователя. Aggregator читает действия и публикует Avro-сходства в `stats.events-similarity.v1`, ключ пары — `eventA:eventB`, всегда `eventA < eventB`. Analyzer независимо читает оба топика, сохраняет данные и предоставляет три server-streaming метода: `GetRecommendationsForUser`, `GetSimilarEvents`, `GetInteractionsCount`.

Для пары «пользователь — мероприятие» хранится максимальный вес действия: по умолчанию `VIEW=0.4`, `REGISTER=0.8`, `LIKE=1.0`. Повторы и меньший вес не увеличивают оценку. Analyzer отдельно обновляет время последнего взаимодействия. Aggregator обновляет суммы через прирост веса, а сходство вычисляет как `sum(min(wA, wB)) / sqrt(sum(wA) * sum(wB))` по всем пользователям; при нулевом знаменателе результат равен `0`.

При увеличении веса Aggregator публикует сходства только с другими мероприятиями из истории текущего пользователя. Суммы весов при этом учитывают всех пользователей. Если изменился только знаменатель пары вне этой истории, её сохранённое сходство обновится при следующем увеличении веса общего пользователя.

Персональные рекомендации начинают с последних `10` взаимодействий (`stats.recommendations.history-size`). Незнакомые пользователю кандидаты объединяются по максимальному сходству и ограничиваются размером запроса. Прогноз кандидата — взвешенное по сходству среднее весов по `5` ближайшим известным мероприятиям (`stats.recommendations.neighbors-size`); соседи выбираются из всей истории, не только из последних десяти. Итог сортируется по прогнозу убывающе, затем по ID возрастающе. Запросы к БД и обогащение ответов пакетные.

Для Aggregator нужен один экземпляр и одна партиция топика действий: матрица целиком принадлежит одному обработчику. При назначении партиции он восстанавливает память чтением истории с начала; уже подтверждённые сходства повторно не публикует. Смещение нового действия подтверждается после отправки всех сходств. Для восстановления нельзя удалять историю действий: локальный Compose задаёт обоим stats-топикам неограниченное хранение. Следите за диском и сохраняйте том Kafka и БД Analyzer.

## Внутренний API

Сервисы вызывают эти методы непосредственно через Eureka/Feign, не через внешний Gateway.

| Сервис | Метод и путь | Вход и результат |
| --- | --- | --- |
| `user-service` | `GET /internal/users/{id}` | `{id, name}`; неизвестный пользователь — `404` |
| `user-service` | `POST /internal/users/lookup` | Массив ID → массив `{id, name}` найденных пользователей; пустой вход → `[]` |
| `event-service` | `GET /internal/events/{id}` | `{id, initiatorId, state, participantLimit, requestModeration}`; неизвестное мероприятие — `404` |
| `request-service` | `POST /internal/requests/confirmed-counts` | Массив ID мероприятий → объект «ID: число подтверждённых заявок»; отсутствующий счётчик означает `0` |
| `request-service` | `GET /internal/requests/users/{userId}/events/{eventId}/confirmed` | `true` только для подтверждённой заявки указанного пользователя на указанное мероприятие |

Внутренние HTTP-методы очистки заменены событиями Kafka; DELETE с телом больше не используется.

## Недоступность зависимостей

Чтение и изменение сохранённых мероприятий, а также создание и изменение подборок не зависят от доступности вспомогательных данных для ответа. При временной недоступности сервиса пользователей сохраняется настоящий ID инициатора, имя отображается как «Имя временно недоступно». При отказе заявок счётчик для отображения равен `0`. Публикация и отклонение мероприятия также продолжают работать. В подборках счётчики остаются `0`, как в исходной реализации; рейтинги загружаются одним запросом для всех уникальных мероприятий подборок.

Для отображения пользователей и заявок предусмотрены два независимых CircuitBreaker. Чтение выполняется максимум за две попытки с паузой `100` мс между ними. После открытия CircuitBreaker новые обращения пропускаются на `5` секунд, затем пробный запрос проверяет восстановление. Значения меняются в Config Server.

Резервные значения используются только для отображения. Проверки владельца, состояния, даты и категории мероприятия сохраняются. При создании мероприятия пользователь должен быть подтверждён сервисом пользователей: его недоступность даёт `503` без создания записи. При `onlyAvailable=true` число подтверждённых заявок должно быть настоящим: недоступность этого счётчика даёт `503`, даже если обычный список доступен. Для распределённой очистки при удалении действуют отдельные правила, описанные ниже. Ошибки `4xx`, некорректный ответ и ошибки программирования не маскируются резервными данными.

Недоступность рекомендательной системы не закрывает каталог: при временном отказе Collector действие пропускается, при отказе Analyzer рейтинг для отображения равен `0`, рекомендации — `[]`. У двух gRPC-клиентов независимые CircuitBreaker и deadline `1` секунда. Автоматического повтора отправки действий нет. Доставка действий не гарантирована: пропущенные действия не сохраняются в outbox и позднее не восстанавливаются. Временный отказ Collector после сохранения заявки не отменяет её; постоянные ошибки контракта и программирования не маскируются резервными данными.

Сервисы заявок и комментариев повторяют временно неудачный GET один раз с паузой `100` мс; POST автоматически не повторяется. Повторы выполняет LoadBalancer, без второго вложенного механизма. При отказе соседнего сервиса непустые локальные заявки и комментарии доступны только своему пользователю. Имя автора заменяется на «Имя временно недоступно». Пустой список без подтверждения существования возвращает `503`. Для выдачи участников мероприятия по-прежнему нужен настоящий ответ `event-service` и проверка владельца. Известные `404`, ошибки формата ответа и запись новых данных не получают резервного подтверждения.

## Фоновая очистка

`DELETE /admin/users/{id}` в одной локальной транзакции удаляет пользователя и сохраняет `USER_DELETED` в `cleanup_outbox`. Ответ `204` означает удаление пользователя и постановку очистки в очередь, а не завершение очистки всех баз. Kafka и соседние сервисы не участвуют в этой HTTP-транзакции.

Отправитель читает ограниченный пакет outbox и удаляет его записи только после подтверждения брокера. `event-service` атомарно фиксирует полученное уведомление в `cleanup_inbox`, сохраняет снимок ID мероприятий в своём outbox и удаляет мероприятия. Сообщение `USER_EVENTS_DELETED` позволяет удалить заявки и комментарии к этим мероприятиям. Заявки и комментарии самого пользователя удаляются также по `USER_DELETED`.

Сообщения передаются в топик `ewm.user-data-cleanup.v1`, ключ — ID пользователя. JSON содержит `eventId` (UUID уведомления), `type`, `userId`, `eventIds`. У трёх потребителей отдельные группы: каждый получает всю очистку. Повторная доставка допустима: event-service распознаёт UUID, остальные выполняют идемпотентное удаление. Маркеры запрещают поздние связанные записи после обработки уведомления; мгновенной согласованности между базами нет.

При отказе брокера уведомления остаются в outbox, при временной ошибке БД обработчик повторяет сообщение без пропуска смещения. После восстановления очистка продолжается без повторного HTTP DELETE. Некорректное сообщение останавливает соответствующий потребитель: причину нужно устранить перед перезапуском, сообщение не пропускается молча.

Для восстановления нужны сохранённые базы и том Kafka. Срок хранения сообщений в топике не ограничен, поэтому в длительно работающем окружении нужно следить за диском. Пример ниже использует один локальный брокер и не обеспечивает сохранность при потере его тома.

Проверка мероприятия для заявки использует снимок параметров, полученный перед локальной транзакцией. Последующее изменение лимита или правил мероприятия не синхронизируется распределённой блокировкой; атомарность статусов и проверки числа заявок обеспечивается внутри `request-service`.

## Локальный запуск

Нужны Java `21` и Maven. Из корня проекта соберите приложения и выполните тесты, Checkstyle и SpotBugs:

```powershell
mvn -B -Pcheck clean verify
```

Сначала запустите общий брокер и отдельную PostgreSQL Analyzer в Docker Desktop:

```powershell
docker compose -p graduation-cleanup -f docker-compose.kafka.yml up -d
docker compose -p graduation-recommendations -f docker-compose.yml up -d analyzer-db
```

Запускайте команды из корня проекта, каждую в отдельном PowerShell-терминале. Перед запуском в каждом терминале приложений `core`, `stats` и Config Server задайте адрес локального брокера:

```powershell
$env:KAFKA_BOOTSTRAP_SERVERS = 'localhost:29092'
```

Переменная одного терминала не распространяется на остальные. Повторите её установку перед каждой соответствующей командой ниже; иначе приложение выберет `localhost:9092`. Дождитесь запуска Eureka и регистрации Config Server, затем запускайте Collector, Aggregator, Analyzer, приложения данных и Gateway:

```powershell
java -jar infra/discovery-server/target/discovery-server-0.0.1-SNAPSHOT.jar
java -jar infra/config-server/target/config-server-0.0.1-SNAPSHOT.jar --server.port=18088
java -jar stats/collector/target/collector-1.0-SNAPSHOT.jar
java -jar stats/aggregator/target/aggregator-1.0-SNAPSHOT.jar
java -jar stats/analyzer/target/analyzer-1.0-SNAPSHOT.jar
java -jar core/user-service/target/user-service-0.0.1-SNAPSHOT.jar --server.port=18081
java -jar core/event-service/target/event-service-0.0.1-SNAPSHOT.jar --server.port=18082
java -jar core/comment-service/target/comment-service-0.0.1-SNAPSHOT.jar --server.port=18084
java -jar core/request-service/target/request-service-0.0.1-SNAPSHOT.jar --server.port=18085
java -jar infra/gateway-server/target/gateway-server-0.0.1-SNAPSHOT.jar
```

Порты выше — HTTP-порты примера локального запуска; взаимные вызовы используют имена Eureka, а не эти порты. У приложений `stats` HTTP-порты Actuator остаются случайными; отдельные gRPC-порты Collector и Analyzer также случайные и передаются через metadata Eureka. Проверьте регистрацию приложений на `http://localhost:8761/`. Пока реестр клиентов обновляется, первые обращения могут временно вернуть `503`, а статистика — резервные значения.

Файловые H2 сохраняются в `./data` между запусками. Не удаляйте их или том Kafka, пока есть необработанные уведомления. Для PostgreSQL задайте отдельное подключение каждому приложению. `docker-compose.yml` запускает БД Analyzer отдельной командой выше; прежний `ewm-db` для четырёх приложений `core` не требуется. `docker-compose.kafka.yml` запускает общий брокер и инициализирует stats-топики; топик очистки создают приложения `core`.

## Проверки API и отказов

Проверяйте основной HTTP API и комментарии через `http://localhost:8080`. Старые коллекции REST-статистики с `/hit`, `/stats`, полем `views` и карточкой без `X-EWM-USER-ID` не соответствуют третьему этапу. gRPC-операции Collector и Analyzer проверяются напрямую по их контрактам, не через HTTP Gateway.

Для сквозной проверки отправьте действия нескольких пользователей на разные мероприятия, дождитесь обработки Kafka и запросите рекомендации с `X-EWM-USER-ID`. Убедитесь, что рейтинг сохраняет дробную часть, знакомые пользователю и неопубликованные мероприятия не выдаются, каталог не создаёт `VIEW`, а отказ проверки участия не разрешает лайк.

Для проверки отказов используйте файловые БД или PostgreSQL, чтобы остановка сервиса не удаляла данные. Создайте опубликованное мероприятие, подтверждённую заявку и подборку. По очереди остановите сервисы заявок, пользователей, Collector, Analyzer и комментариев: чтение и изменение сохранённых мероприятий, публикация/отклонение, создание и изменение подборок должны работать с резервными данными для ответа. Операции, которым недоступные данные нужны для бизнес-проверки, продолжают возвращать `503`. После восстановления проверьте настоящие имена, счётчики, рейтинги и сохранность изменений. В завершение остановите инфраструктуру и остальные приложения: работающий `event-service` должен самостоятельно читать мероприятия, категории и подборки, изменять свои мероприятия и создавать/изменять подборки на своём порту. Создание мероприятия без проверки пользователя и обход проверки владельца не допускаются.
