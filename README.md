# Explore With Me

Сервис поиска мероприятий, заявок на участие и комментариев. Второй этап диплома: отдельные приложения взаимодействуют по HTTP, а внешние запросы проходят через Gateway на порту `8080`.

## Архитектура

| Приложение | Ответственность и собственные данные |
| --- | --- |
| `discovery-server` | Реестр Eureka, порт `8761` |
| `config-server` | Настройки приложений из `infra/config-server/src/main/resources/config-repo` |
| `gateway-server` | Единая точка входа, маршрутизация по именам сервисов через LoadBalancer |
| `user-service` | Пользователи, таблица `users` |
| `event-service` | Мероприятия, категории, подборки и их связи; маркеры очистки пользователя |
| `request-service` | Заявки и их статусы; маркеры очистки пользователей и мероприятий |
| `comment-service` | Комментарии; маркеры очистки пользователей и мероприятий |
| `stats-server` | Записи посещений и статистика просмотров |

Каждый сервис данных подключается к своей БД и выполняет собственные миграции Flyway. Между базами нет внешних ключей и прямых SQL-запросов: ссылка на чужую сущность хранится как идентификатор. Старый `main-service` заменён четырьмя приложениями в `core`.

`user-client` и `event-client` содержат общие контракты и Feign-клиенты, `api-errors` — общий формат ошибок. Они не включают реализации сервисов или чужие JPA-сущности. Статистика использует отдельный `stats-client` с LoadBalancer.

При создании заявки и комментария пользователь и мероприятие проверяются по HTTP. Списки обогащаются пакетными запросами: имена пользователей и подтверждённые заявки загружаются для набора идентификаторов, а не отдельно для каждого мероприятия. Сетевые вызовы выполняются вне транзакций БД; связанные локальные изменения — в короткой транзакции.

## Конфигурация

Клиенты находят `config-server` через Eureka и загружают общие настройки из `config-repo/application.yml` и YAML своего приложения. Настройки приложения имеют приоритет над общими. Config Server работает с профилем `native` и каталогом `classpath:/config-repo/`; его конфигурация и адрес Eureka находятся в `application.properties` инфраструктурных модулей. Локальные настройки клиентов сохраняют имя приложения, адрес Eureka и параметры получения конфигурации.

- `EUREKA_SERVER_URL` задаёт адрес Eureka; по умолчанию `http://localhost:8761/eureka/`.
- `--server.port` переопределяет порт приложения. Кроме Gateway и Eureka, порты по умолчанию случайные.
- У каждого сервиса данных свои `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`. По умолчанию используются отдельные H2 в режиме совместимости с PostgreSQL.
- Flyway создаёт схему, Hibernate проверяет её через `ddl-auto=validate`; `open-in-view` отключён.
- Таймауты Feign: подключение `1000` мс, чтение `2000` мс. Настройки резервного отображения и статистики находятся в `event-service.yml`.

Не задавайте один общий адрес БД всем приложениям. Миграции новых сервисов рассчитаны на отдельные новые базы, а не на автоматическое преобразование старой БД монолита.

## Внешний API

Все запросы отправляются на `http://localhost:8080`. Пути и форматы сохранены:

| Пути | Получатель |
| --- | --- |
| `/admin/users/**` | `user-service` |
| `/users/{userId}/events/{eventId}/comments` и вложенные пути | `comment-service` |
| `/users/{userId}/requests`, вложенные пути; `/users/{userId}/events/{eventId}/requests`, вложенные пути | `request-service` |
| Остальные `/admin/**`, `/users/**`, `/events/**`, `/categories/**`, `/compilations/**` | `event-service` |
| `/hit`, `/stats` | `stats-server` |

Более узкие маршруты пользователей, комментариев и заявок проверяются перед общим маршрутом событий. Gateway не публикует `/internal/**`.

Основные контракты: [API мероприятий](ewm-main-service-spec.json), [API статистики](ewm-stats-service-spec.json). Дополнительные сценарии комментариев: [Postman-коллекция](postman/feature.json).

## Внутренний API

Сервисы вызывают эти методы непосредственно через Eureka/Feign, не через внешний Gateway.

| Сервис | Метод и путь | Вход и результат |
| --- | --- | --- |
| `user-service` | `GET /internal/users/{id}` | `{id, name}`; неизвестный пользователь — `404` |
| `user-service` | `POST /internal/users/lookup` | Массив ID → массив `{id, name}` найденных пользователей; пустой вход → `[]` |
| `event-service` | `GET /internal/events/{id}` | `{id, initiatorId, state, participantLimit, requestModeration}`; неизвестное мероприятие — `404` |
| `event-service` | `DELETE /internal/users/{userId}/data` | Очистка связанных данных пользователя, успешный ответ `204` |
| `request-service` | `POST /internal/requests/confirmed-counts` | Массив ID мероприятий → объект «ID: число подтверждённых заявок»; отсутствующий счётчик означает `0` |
| `request-service` | `DELETE /internal/requests/users/{userId}` | Тело — массив ID мероприятий пользователя; очистка его заявок и заявок на его мероприятия, ответ `204` |
| `comment-service` | `POST /internal/users/{userId}/comments/cleanup` | Тело — массив ID мероприятий пользователя; очистка его комментариев и комментариев к его мероприятиям, ответ `204` |

## Недоступность зависимостей

Чтение и изменение сохранённых мероприятий, а также создание и изменение подборок не зависят от доступности вспомогательных данных для ответа. При временной недоступности сервиса пользователей сохраняется настоящий ID инициатора, имя отображается как «Имя временно недоступно». При отказе заявок счётчик для отображения равен `0`. Публикация и отклонение мероприятия также продолжают работать. В подборках счётчики и просмотры остаются `0`, как в исходной реализации.

Для отображения пользователей и заявок предусмотрены два независимых CircuitBreaker. Чтение выполняется максимум за две попытки с паузой `100` мс между ними. После открытия CircuitBreaker новые обращения пропускаются на `5` секунд, затем пробный запрос проверяет восстановление. Значения меняются в Config Server.

Резервные значения используются только для отображения. Проверки владельца, состояния, даты и категории мероприятия сохраняются. При создании мероприятия пользователь должен быть подтверждён сервисом пользователей: его недоступность даёт `503` без создания записи. При `onlyAvailable=true` число подтверждённых заявок должно быть настоящим: недоступность этого счётчика даёт `503`, даже если обычный список доступен. Для распределённой очистки при удалении действуют отдельные правила, описанные ниже. Ошибки `4xx`, некорректный ответ и ошибки программирования не маскируются резервными данными.

Недоступность статистики не закрывает каталог: регистрация посещения пропускается, просмотры отображаются как `0`. Общий CircuitBreaker защищает поиск инстанса и HTTP-вызов. Повторяется только поиск сервиса; `POST /hit` автоматически не повторяется, чтобы не записать одно посещение дважды. Пропущенные посещения позднее не восстанавливаются.

Удаление пользователя — последовательная очистка комментариев, заявок и мероприятий, затем удаление самого пользователя. Это не распределённая транзакция: при сбое часть очистки могла завершиться. Маркеры запрещают новые связанные записи; после восстановления нужно повторить удаление того же пользователя. Операции очистки рассчитаны на повтор, посторонние данные не удаляются.

Проверка мероприятия для заявки использует снимок параметров, полученный перед локальной транзакцией. Последующее изменение лимита или правил мероприятия не синхронизируется распределённой блокировкой; атомарность статусов и проверки числа заявок обеспечивается внутри `request-service`.

## Локальный запуск

Нужны Java `21` и Maven. Из корня проекта соберите приложения и выполните тесты, Checkstyle и SpotBugs:

```powershell
mvn -B -Pcheck clean verify
```

Запускайте команды из корня проекта, каждую в отдельном терминале. Сначала дождитесь запуска Eureka и регистрации Config Server, затем запускайте приложения данных и Gateway:

```powershell
java -jar infra/discovery-server/target/discovery-server-0.0.1-SNAPSHOT.jar
java -jar infra/config-server/target/config-server-0.0.1-SNAPSHOT.jar --server.port=18088
java -jar core/user-service/target/user-service-0.0.1-SNAPSHOT.jar --server.port=18081
java -jar stats/stats-server/target/stats-server-1.0-SNAPSHOT.jar --server.port=18083
java -jar core/event-service/target/event-service-0.0.1-SNAPSHOT.jar --server.port=18082
java -jar core/comment-service/target/comment-service-0.0.1-SNAPSHOT.jar --server.port=18084
java -jar core/request-service/target/request-service-0.0.1-SNAPSHOT.jar --server.port=18085
java -jar infra/gateway-server/target/gateway-server-0.0.1-SNAPSHOT.jar
```

Порты выше — пример локального запуска; взаимные вызовы используют имена Eureka, а не эти порты. Проверьте регистрацию приложений на `http://localhost:8761/`. Пока реестр клиентов обновляется, первые обращения могут временно вернуть `503`.

H2 в памяти подходит для нового проверочного запуска, но данные исчезают при остановке приложения. Для проверки перезапуска задайте каждому сервису отдельную файловую H2 или PostgreSQL через параметры подключения. Docker не требуется для приведённого запуска; старый `docker-compose.yml` не запускает новую микросервисную схему.

## Проверки API и отказов

Запускайте коллекции основного API, статистики и комментариев с адресом `http://localhost:8080`. Если подготовительный скрипт коллекции статистики выбирает прямой порт из Eureka, замените только подготовку адреса на Gateway, сохранив проверки и тела запросов.

Для проверки отказов используйте файловые БД или PostgreSQL, чтобы остановка сервиса не удаляла данные. Создайте опубликованное мероприятие, подтверждённую заявку и подборку. По очереди остановите сервисы заявок, пользователей, статистики и комментариев: чтение и изменение сохранённых мероприятий, публикация/отклонение, создание и изменение подборок должны работать с резервными данными для ответа. Операции, которым недоступные данные нужны для бизнес-проверки, продолжают возвращать `503`. После восстановления проверьте настоящие имена, счётчики и сохранность изменений. В завершение остановите инфраструктуру и остальные приложения: работающий `event-service` должен самостоятельно читать мероприятия, категории и подборки, изменять свои мероприятия и создавать/изменять подборки на своём порту. Создание мероприятия без проверки пользователя и обход проверки владельца не допускаются.
